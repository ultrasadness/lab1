# Live state is a SQLite store the bot alone writes, and an uncertain step counts as done

English | [中文](0007-live-state-in-sqlite-and-an-uncertain-step-counts-as-done.zh.md)

Everything that changes as work moves is kept in one SQLite file on the VM, beside the git-tracked Personal database: the mail ledger and Gmail `historyId`, each Launch's verdict, each Registration's and Reply draft's current state, Approvals, and the marks that make a step happen once. The bot is its only writer and it is the single source of truth for that state. The Personal database in git gets each Registration's history as readable lines, which the bot writes at milestones (approved, submitted, outcome). The brief asks for a Markdown Personal database, so a reader would expect the ledger there. But a state that changes every few seconds while a Registration waits for verification would mean a commit each time. And by [ADR 0002](./0002-rules-are-files-proven-by-their-own-case.md)'s commit lock, the bot stops committing when histories diverge, so one stray git edit would freeze the ledger and stall the Assistant. Decided in [How do Registration and Reply draft states move, and how is double-handling prevented?](https://github.com/ultrasadness/lab1/issues/11).

## Considered Options

- **Everything in the git-tracked Personal database, one commit per change:** the person could read every state in place. Rejected for the commit volume and because a diverged history would stop all work, not just Rule edits.
- **State as YAML front matter the person may edit in git, read back by the bot:** every edit would have to be checked against the state machine, and a hand-edited state could skip a once-only step. The person changes a Registration's state from Discord instead.

## Consequences

- **The Markdown record is a view.** The bot writes it from the store and never reads state edits back from git. Each Product's folder in the Personal database keeps it as `registration.md`, beside the Dossier's `dossier.md`. The person's free-text notes sit in a third file, `notes.md`, which the bot creates once and never writes again, so nothing the bot writes can touch them. Decided in [How does a Dossier read in its Product post, and how is it kept in git?](https://github.com/ultrasadness/lab1/issues/33), replacing the notes section this ADR first recorded. Each Miner day gets the same kind of view, `days/<YYYY-MM-DD>.md`: the Day's line and one line per Featured Launch, rewritten when a Correction changes the day. Every date the bot writes into the Personal database carries its year (`2026-10-14 08:12 PT`), so a Question can filter by date. Both decided in [How does the person ask the Personal database a question from Discord?](https://github.com/ultrasadness/lab1/issues/37).
- **Once-only steps are written ahead.** Before plain code presses a button, opens a verification link or sends a Reply draft, it writes an _intended_ mark (the item, the step, a fingerprint of the page or the approved bytes), acts, then writes _done_.
- **An uncertain step counts as done, and is never retried automatically.** After a restart or a timeout, an _intended_ without _done_ means the account may exist. A press counts as pressed, and the Registration moves on to waiting for verification. The person is told what was uncertain. A send can be read back: if the thread shows no new `SENT` message and the draft still holds the approved message, it wasn't sent and may be sent again. So can a vault item's create, whose item holds the only copy of its password and whose id the bot needs: the Password vault shows whether the item is there, and only if it isn't is one made ([#54](https://github.com/ultrasadness/lab1/issues/54)). A Takeover that ends without the person saying nothing was submitted also counts as submitted. The same reading is behind [ADR 0006](./0006-registration-browser-in-its-own-container-driven-through-fixed-actions.md)'s rule that, after a browser-service restart, a Registration whose final button was pressed waits for the person's tap in Gmail.
- **The person's word settles an uncertain press; plain code never does.** In a Takeover, **Continue** means no account was made, even after a press the Product visibly rejected. The Registration then goes back to the page check, and the next press gets a new _intended_ mark. If the same form still shows on the same URL 10 seconds after a final press, plain code only tells the person, with **Take over** and **Hand off**. The state doesn't change on its own. Decided in [What happens when a Registration hits a wall, and where do borderline in-page actions fall?](https://github.com/ultrasadness/lab1/issues/10).
- **Approvals are keyed by item and version hash**, unique in the store, with the Discord user id, interaction id and time. A second tap of an approved version does nothing, and a tap on an older version is refused.
- **Mail and Launches are handled once by key:** the ledger by Gmail message ID, written before the stored `historyId` advances; Launches by Product Hunt Post id; Products by root domain.
- **A mail's disposition moves at most once, and only from a waiting one.** _Unmatched_, _held_ (over the cap, quiet, or not followed) and _not handled_ (stopped or waiting) may each move once to a final disposition, through **From a Product…**, **Read it**, or a **Retry** or route coming back. Each move adds a row with its time and cause, and nothing is overwritten. Plain code sets a hold's reason when the mail arrives and never re-checks it, so following a Product again releases nothing already held. Decided in [What is left to decide before the spec is written?](https://github.com/ultrasadness/lab1/issues/40).
- **If the store is lost,** the Assistant starts from the current Gmail `historyId` and treats all older mail as already seen. Missing a mail is safer than handling one twice. Backing the file up belongs with keeping the Assistant running.
- **Raw inputs kept for 90 days** for Rule cases sit beside the store as plain files, indexed by it, outside git.
