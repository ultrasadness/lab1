# Rules are files our own extension loads, each proven by its own carry-over case

Each Rule is one Markdown file under `rules/<scope>/` in the Personal database, and our own Pi extension puts every Rule in scope into the prompt at the start of each run. A Rule is committed only after the person keeps it. Each Rule carries a carry-over case: the item it was taught on, a different real item where it should change the outcome, and that outcome stated as something a script can check. The brief asks for Corrections that apply to a different item in a new session, and Pi forgets everything between runs, so carrying a Rule over has to be something we build and can prove. Decided in [How does a Correction become a Rule, and how do we prove it carries over?](https://github.com/ultrasadness/lab1/issues/14).

## Considered Options

- **All Rules in `AGENTS.md`:** loads in every run without project trust, but it is one growing file with no scope, so every run would carry every Rule.
- **Each Rule as an Agent Skill:** the model decides whether to open it, and unattended Pi runs skip project skills without `--approve`. Neither can be relied on to load a Rule every time.
- **Raw Corrections retrieved by similarity** instead of general Rules: avoids wording a Rule too narrowly or too broadly. Rejected because the person can't read or edit them as a list of what the Assistant now does, and a retriever deciding which Corrections count can't be tested.
- **A fixed golden suite** instead of a case for every Rule: cheaper and steadier, but most real Rules would never be proven to carry over.

## Consequences

- **The scopes are Miner** (judging and Skips), **Dossier**, **Walkthrough/Registration**, **mail**, and **all**. The mail scope loads into mail runs and Reply draft runs alike, because a mail run chooses which mail gets a Reply draft and a Correction can say it chose wrong. It was named *Reply draft* until [Which matched mail gets a Reply draft, and what does the Assistant draw on to write it?](https://github.com/ultrasadness/lab1/issues/32).
- **Outputs name the Rules they applied**, through a field in each schema-checked record. A case passes only when the Rule is named and the expected outcome holds, in at least 2 of 3 fresh runs. When a case is created, it must also fail without the Rule.
- **Cases replay stored inputs**, kept beside the Rule: Launch data as the API returned it, mail with Secrets already replaced by placeholders, and the page text a Walkthrough saw. No case opens a live browser, and no fixture holds a Secret. Raw inputs are kept for 90 days outside git so that cases can be built from past items. A mail fixture is the exception to "beside the Rule": it sits in a local fixture store on the VM, outside git, until its Rule retires, and the Rule points to it by ID ([ADR 0010](./0010-mail-text-reaches-only-mail-cleared-roles-on-routes-that-dont-train.md)).
- **The check runs against every provider mapped to the Rule's role:** when a Rule is kept, after a Rule is edited, before every upgrade (a failure blocks it unless the person overrides it), and weekly to catch a provider quietly changing the model behind a pinned name. It reaches each provider through a model name that only that provider serves (e.g. `miner@openrouter`), which `ops/upgrade role` creates and removes with the role's mapping, because an ordinary new-api key can't pick a channel ([How do we catch a Miner provider whose Fits run higher or lower than the others?](https://github.com/ultrasadness/lab1/issues/35)).
- **The Rules loaded into one run have a budget**, always called **the Rule budget** (about 4k tokens), so it isn't confused with the spending budgets of [ADR 0011](./0011-the-forwarder-picks-each-requests-provider-and-holds-the-spending-budgets.md). Near the Rule budget, the Assistant proposes merging overlapping Rules, and the merged Rule inherits their cases. Rules nobody has cited in 60 days are offered for retirement.
